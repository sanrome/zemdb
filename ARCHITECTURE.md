# Architectural Specification: ZemDB (Local-First Distributed Database Engine)

## 1. Overview
The goal of this project is to build a client-centric (**Local-First**) distributed database engine powered by a **minimal, lightweight coordination server**.

* **Primary Storage:** 100% stored locally on clients in a structured, persistent format.
* **Server Role:** Acts as a sequencer, schema/type validator, and ephemeral mutation buffer. The server **does not maintain the long-term historical state** of each database; it only holds unread mutations until clients acknowledge them or a retention threshold expires.
* **Performance Objective:** Ultra-low server memory and CPU footprint, capable of coordinating numerous groups with minimal resource consumption.

---

## 2. Topology & Isolation (Rooms & Schema Catalog)
The system adopts an isolated **Room** topology governed by a centralized **Schema Catalog**:
* **Compartmentalized Rooms:** Each database is an independent compartment identified by a strongly-typed `RoomId` (e.g., a chat group, team workspace, or specific collaborative project).
* **Small-to-Medium Groups:** A room typically consists of a small-to-medium group of clients (e.g., 2 to 50 participants).
* **Centralized Schema Catalog (`SchemaId` Hierarchy):** A `Schema` is an independent template identified by a `SchemaId` (e.g., `workspace_v1`). Multiple rooms share the same `SchemaId`, allowing the server to maintain a single `Arc<Schema>` in memory across thousands of rooms without duplicating table definitions or memory overhead. Each room contains exactly one flat schema (no sub-namespaces or sub-schemas), keeping room lookups and storage paths predictable and fast.
* **Per-Room Scoping:** Operations, physical WAL files, and sequence numbers are strictly scoped to their respective Room.

## 3. Data Model & Schema

### 3.1. Structured Typing & Schema Definitions
Every table within a Schema has an explicit definition with typed fields:
* **Primitive Data Types:** `Int`, `Float`, `String`, `Bool`, `Bytes`, `Null`, `Timestamp` (domain date/time), and `Uuid` (`[u8; 16]` fixed-size, ideal for distributed primary keys). Arbitrary-precision `Decimal` is deferred to post-v0.1.
* **Strongly-Typed Domain Identifiers & Encapsulated Models (C-DEREF Compliance):** Domain identities (`RoomId`, `SchemaId`, `ClientId`, `SequenceNumber`, `MutationId`, `CorrelationId`) and data models (`PrimaryKey`, `CompactRow`, `TableSchema`) are fully encapsulated with private inner representations. In strict accordance with Rust API Guidelines [C-DEREF], implicit `Deref` coercions are eradicated across all core structures to protect type abstraction boundaries and prevent accidental mutation of internal vectors or strings. String identifiers are validated by construction ("parse, don't validate"): `RoomId::new`, `SchemaId::new` and `ClientId::new` return `Result`, and deserialization (JSON, bincode) validates as well, so no code path can hold an invalid identifier, whatever its source (URL, binary payload, admin JSON, files on disk, or the `zemdb-storage` API). `RoomId` and `SchemaId` are used as file and directory names, so they are restricted to lowercase ASCII letters, digits, `-` and `_` (1 to 64 characters), excluding Windows reserved device names: this rules out path traversal (`/`, `..`) and collisions on case-insensitive file systems (macOS, Windows). `ClientId` is never used in paths and accepts any text of 1 to 256 bytes without control characters, without leading or trailing whitespace, and without the invisible, formatting, filler, variation-selector, tag and bidirectional control characters most used for spoofing (such as zero-width spaces, soft hyphens, BOM and bidi overrides). This is a denylist, not a guarantee that two distinct client IDs never look alike: no Unicode normalization is applied. Tokens bind the exact bytes, so this only affects display, never authentication. Validation errors echo at most 80 characters of the rejected input. Ergonomics and zero-overhead performance are maintained through explicit accessors (`as_str()`, `get()`, `as_bytes()`, `columns()`, `column_indices()`), standard trait indexing (`Index<usize>`, `IndexMut<usize>`), iterator APIs (`iter()`, `as_slice()`), trait conversions (`AsRef<str>`, `AsRef<[u8]>`, `AsRef<[Value]>`, `From`), and compact Serde representations: numeric and byte identifiers are `#[serde(transparent)]`, while the string identifiers use `#[serde(try_from = "String", into = "String")]`, so they are still serialized as plain strings but validated on deserialization.
* **In-Memory Density & Cache-Line Alignment:** Tuples are stored positionally (`CompactRow`) without duplicating column names across rows. The dynamic `Value` enum is strictly bounded to **24 bytes** on 64-bit platforms (by boxing heap payloads: `String(Box<str>)` and `Bytes(Box<[u8]>)`). Primary keys are optimized with `SmallVec<[Value; 1]>` occupying **40 bytes** on the stack, strictly fitting within a single 64-byte CPU L1 cache line to prevent cache line splits during index lookups.
* **Compact Table Identifiers (`table_id: u16`):** Every table in a Room is assigned a compact 2-byte numerical identifier (`table_id: u16`). Strings are completely eliminated from the inner mutation loop and memory storage structures. The `Schema` maintains a bidirectional catalog with explicit, unambiguous lookup methods: `get_table_by_id`, `get_table_by_name`, `get_table_id`, `has_table_by_id`, and `has_table_by_name`. Secondary indexing (`id_by_name`) is dynamically constructed upon deserialization and omitted from network/disk serialization. Both maps are private: the catalog changes only through `Schema::insert_table` (strict: the table keeps its own id, and a repeated id or name is an error) and `Schema::add_column` (append-only evolution of a table), and is read through the lookups above plus `tables()`, `table_ids()` and `table_count()`. `TableSchema` and `ColumnDef` encapsulate their fields privately, exposing immutable getters; a column can only be changed before it belongs to a table.
* **Strict Table IDs:** Operations in the WAL, snapshots and client outboxes refer to tables by id, so ids are never reassigned. A schema is serialized (admin JSON, `schemas/{id}.json`, protocol messages) as `{"tables": [table, ...]}` in ascending id order, every table carrying its own `table_id`; deserialization inserts them strictly and fails on a repeated id or name, a table without `table_id`, or an unknown field (such as a map keyed by id, which could disagree with the ids inside it). It never assigns an id. Ids are assigned only when building a schema programmatically: `SchemaBuilder::table` takes a `TableBuilder` whose id is optional and gives a table without one the id after the largest so far (0 for the first); an explicit id is kept and must be unique. `TableBuilder::build`, which produces a standalone `TableSchema`, requires an explicit id.
* **Unified Stack-Allocated Mutation Unit (`Operation`):** All row mutations are represented by a single unified, stack-allocated `Operation` struct (`table_id: u16`, `timestamp: u64`, `pk: PrimaryKey`, `kind: OperationKind`) occupying **exactly 88 bytes** on 64-bit systems with 0 bytes heap overhead for metadata. Its fields (and those of `ColumnUpdate`) are read through accessors and cannot be mutated outside `zemdb-core`; the constructors keep update deltas sorted by `column_idx`. This is not a validity guarantee: `Operation` is a wire type, and one decoded from a client message or a WAL record arrives through `Deserialize` as it was encoded. The guarantee is `Schema::validate_operation`, which the server and both storage engines run on every operation before using it.
* **Dense Sequenced Operations (`SequencedOperation`):** Historical log records compose a 64-bit monotonic sequence number with the mutation: `SequencedOperation { seq: SequenceNumber, op: Operation }`, occupying **exactly 96 bytes**. Ephemeral client metadata (`client_id`, `mutation_id`) is retained strictly in transit during `Commit` / `CommitAck` for idempotency and 1-RTT synchronization, eliminating 24 bytes of overhead per historical operation in RAM and persistent storage.
* **Deterministic Column Ordering (Append-Only DDL):** `TableSchema` preserves physical column declaration order in `columns: Vec<ColumnDef>`, ensuring stable positional binary offsets in `CompactRow` across schema migrations, paired with zero-copy row transformations (`row_into_compact` and `compact_into_row`). `compact_into_row` and `from_compact_row` support backward evolution where `compact.len() <= self.columns.len()` by treating omitted columns as `Value::Null`. In `StorageEngine::apply_batch`, tuples are dynamically resized upon `Update` operations targeting newly added column indices. Dynamic schema evolution (`TableSchema::add_column`) strictly enforces that newly appended columns must be nullable (`nullable: true`) to preserve backward integrity over historical records. Columns are addressed by a `u16` positional index, so a table holds at most `MAX_COLUMNS` (65,535) columns; building, deserializing or evolving a table past that is `ValidationError::TooManyColumns`.
* **Native $O(C)$ Positional Mutation Validation:** Positional validation algorithms (`TableSchema::validate_operation` and `TableSchema::validate_column_updates`) evaluate compact rows and sorted `ColumnUpdate` deltas directly in $O(C)$ linear time against column definitions, verifying types, nullability, E2EE constraints, and strictly ascending column index order without allocating or reconstructing intermediate `HashMap<String, Value>` instances.
* **End-to-End Encryption (E2EE):** Handled via metadata on `ColumnDef` (`encrypted: bool`). The schema preserves the real underlying `data_type` for client-side decryption, while the coordination server validates that encrypted fields in transit are transmitted strictly as opaque `Value::Bytes` without inspecting payload contents. Primary key columns cannot be encrypted. The `CryptoEngine` contract incorporates conditional `CryptoConcurrencyBounds` (`Send + Sync` on native, relaxed on `wasm32`) and authenticated additional data (`aad: &[u8]`, providing `(table_id, pk, column_idx)`) to cryptographically defend against ciphertext column substitution attacks.
* **Primary Key (PK):** Supports both single-column and composite (multi-column) primary keys.
* **Soft Foreign Keys:** Relational references are supported without distributed locking or strict server-side validation. Dangling references are permitted to maintain eventual consistency without coordination bottlenecks.
* **Schema Evolution:** Supports adding new fields over time without breaking backward compatibility.

## 4. Mutation Operations & Semantics

All mutations are represented by elemental operations structured with decoupled metadata (`table_id: u16`, `pk: PrimaryKey`, `timestamp: u64`) and payload (`OperationKind`):

1. **`INSERT` (`OperationKind::Insert { row: CompactRow }`):**
   * Inserts a new tuple stored positionally in DDL order, eliminating column names from the wire and in-memory tuples.
   * **Semantics on existing PK:** If an `INSERT` is performed on an existing primary key, it operates as a full overwrite (upserting all fields).
2. **`UPDATE` (`OperationKind::Update { updates: Vec<ColumnUpdate> }`):**
   * Granular, field-level modification transmitting only modified fields as 32-byte positional deltas (`ColumnUpdate { column_idx: u16, value: Value }`).
   * **Sorted Invariant & $O(M+N)$ Merges:** Deltas are maintained strictly ordered by ascending `column_idx`, guaranteeing linear sorted merges without heap reallocation or unstable sorting.
   * **Concurrent Conflict Resolution:** If two clients update distinct fields of the same tuple concurrently, the server performs a **field-level merge**. If both clients modify the exact same field, a *Last-Write-Wins (LWW)* policy applies based strictly on the server arrival order and assigned `SequenceNumber` (see Section 10).
3. **`DELETE` (`OperationKind::Delete`):**
   * Logical deletion via a tombstone marker.

### 4.1. Client-Side Consolidation (Outbox Queue Squashing)
In offline scenarios, the client buffers uncommitted mutations in its local outbox queue before transmission to the server. To optimize bandwidth and eliminate redundant operations on the wire, the client can consolidate pending mutations for the same table and primary key using `squash_operations`:
* **Zero-Copy Move Semantics:** Values are transferred by ownership movement (`drain(..)` and slot replacement), eliminating redundant cloning of strings and bytes.
* **Strict Last-Write-Wins (LWW) Causality:** When consolidating an incoming `UPDATE` over an existing `INSERT` (Rule 1), if `incoming.timestamp < existing.timestamp`, the stale update is discarded (`SquashOutcome::Discarded`), preventing obsolete updates from overwriting non-null or null columns.
* **Anti-Zombie Rule:** An `UPDATE` operation arriving after a `DELETE` on the same primary key cannot resurrect deleted records (obsolete updates are `Discarded`; newer updates are `Incompatible`).
* **Base Entity Preservation (Old Insert into Newer Update):** An `INSERT` arriving with an older timestamp than an existing pending `UPDATE` preserves full entity data: the newer update deltas are applied directly over the incoming base `CompactRow`, preventing entity or column loss.
* **Mutual Annihilation & Buffer Purge:** When a pending uncommitted `INSERT` receives a subsequent `DELETE` for the same PK before transmission to the network, both operations mutually annihilate (`SquashOutcome::Purged`). The primary key is completely removed from the buffer, eliminating unnecessary network traffic and avoiding spurious tombstones.
* **Table-Partitioned Buffering (`TableBuffer`):** Buffers hold `table_id: u16` and manage their own private `HashMap<PrimaryKey, Operation>`, ensuring $O(1)$ amortized squashing and zero lock contention between distinct tables. Pending entries change only through `apply` (which enforces the rules above) and `drain`; there is no mutable access to a pending operation. `apply` looks the entry up by reference, so squashing into an existing entry never clones the primary key. A buffer serializes as its table id and the list of pending operations (each keyed by its own primary key); deserialization rejects an operation of another table, a repeated primary key, and update deltas that are not strictly ascending by column index (which squashing relies on).
*(Note: Squashing is strictly a client-side optimization performed prior to transmission. The coordination server never alters, merges, or deletes sequenced operations in the historical log).*

## 5. The Coordination Server (`zemdb-server`)

### 5.1. Core Responsibilities
1. **Monotonic Sequencer:** Assigns an incremental, globally ordered sequence number (`SequenceNumber`: 1, 2, 3...) per Room.
2. **Actor-Based Concurrency:** Manages each Room via an isolated Tokio actor, eliminating global lock contention across rooms. Actors are spawned on demand and shut down when the room is inactive (see [Room Actor Lifecycle](#54-room-actor-lifecycle-inactivity-and-panics)).
3. **Type & Schema Validation:** Enforces schema integrity, required non-null columns, and primary key type constraints before accepting operations.
4. **Idempotency & Deduplication:** Maintains an in-memory LRU cache of recent `MutationId`s (hydrated from the retained log on boot) so that retrying a commit is safe. The guarantee has a window: a retry is recognized only while its `MutationId` is in the cache, which holds the last `dedup_lru_capacity` mutations (10,000 by default) and, after a restart, only those still in the retained log. A retry that arrives after its log segment was pruned (for example after the 30-day cold TTL) is applied again. Clients therefore retry unconfirmed commits only within the session that sent them, never across sessions.
5. **Immutable Tiered Delta Log:** Stores and serves contiguous, immutable `SequencedOperation { seq, op }` deltas across a 4-tier hierarchy without modifying or squashing sequenced operations.
6. **Micro-WAL:** Lightweight append log ensuring safe persistence and recovery of the latest `SequenceNumber` across server restarts.
7. **Ephemeral Snapshot Relay:** Relays compressed multipart snapshot chunks between active clients and onboarding/reconnecting peers without constructing or interpreting database states itself. It keeps at most one snapshot per room, on disk only, for a limited time (see [Snapshot Relay](#snapshot-relay-storage-acceptance-and-limits)).

### 5.2. Four-Tier Storage Architecture & Mutation Lifecycle
To balance minimal RAM usage with flexible offline support, the coordination server manages room mutations across four distinct storage tiers as an **immutable append-only log**:

```
┌─────────────────────────────────────────────────────────────────────────────────┐
│                          4-TIER SERVER STORAGE HIERARCHY                        │
├─────────────────────────────────────────────────────────────────────────────────┤
│ Tier 1: Hot RAM Buffer (Minutes)                                                │
│  - Active connected clients, lowest latency                                     │
│  - Contiguous in-memory log: VecDeque / BTreeMap<SequenceNumber, SequencedOp>   │
│  - Flushed to Warm Disk upon TTL expiration or buffer size threshold            │
├─────────────────────────────────────────────────────────────────────────────────┤
│ Tier 2: Warm Disk Log [.wal] (Days)                                             │
│  - Uncompressed append-only log with 0xBA7C framing and per-batch CRC32         │
│  - Zero CPU overhead, fast sequential streaming for recently offline clients    │
│  - Identical binary representation to in-memory batch payloads                  │
├─────────────────────────────────────────────────────────────────────────────────┤
│ Tier 3: Cold Disk Log [.wal.zst] (Weeks)                                        │
│  - Background Zstandard compression into immutable delta segments               │
│  - High compression ratio saves disk space for long-term offline retention      │
│  - Streamed to reconnecting clients that have been offline for days/weeks       │
├─────────────────────────────────────────────────────────────────────────────────┤
│ Tier 4: Eviction & Compaction Boundary [BehindCompaction]                       │
│  - Operations exceeding the maximum cold retention duration are pruned          │
│  - Reconnecting clients with last_ack_seq < tail_seq receive BehindCompaction   │
│  - Client recovers state via full base snapshot transfer from an active peer    │
└─────────────────────────────────────────────────────────────────────────────────┘
```

1. **Tier 1 (Hot RAM Buffer):**
   * Serves real-time queries and sub-millisecond synchronization for currently connected clients.
   * Holds an immutable contiguous buffer of recent `SequencedOperation`s (`VecDeque`). No squashing is performed on sequenced deltas, ensuring absolute sequence contiguity (`head_seq + 1`) and preventing sequence gaps or zombie record anomalies.
   * Rotates and evicts older operations from RAM when the batch reaches the memory threshold (`ram_max_ops`) or RAM TTL expires, knowing data is already physically safe on disk. The window is applied on every append and, so that an idle room also releases its RAM, on the slow maintenance tick.
2. **Tier 2 (Warm Disk Log - Uncompressed `.wal` con Write-Through):**
   * Stored directly on disk using the standard batch framing (`0xBA7C` magic, length, unified CRC32, operation count, and optional `mutation_id` in `WalBatchPayload`).
   * **Unified Single-WAL Persistence (Zero Desync & Single `fsync`):** Eradicates Dual-WAL and secondary metadata files (`meta_{room_id}.wal` / `MicroWal`). Every accepted mutation is synchronously written to `active.wal` with a single `sync_data()` before confirming `CommitAck`. This eliminates crashes between sequence allocation and operation delta logging, halves commit I/O latency, and hydrates `DedupLruCache` directly from the Warm and Cold segments on boot.
   * When HotBuffer rotates, `active.wal` is sealed as `segment_{start}_{end}.wal`. Remains uncompressed to avoid CPU decompression spikes when clients reconnect after hours or days.
   * **Durable directory entries:** the segments directory is synced after `active.wal` is sealed by rename, and when a fresh `active.wal` is created (before its first record is acknowledged), so a power loss can neither lose a sealed segment nor the file holding acknowledged commits. Directory syncs only exist on Unix; on Windows they are a no-op (a directory cannot be opened as a file there, and NTFS journals directory changes).
   * **Failed append stops the room:** if writing or syncing a record to `active.wal` fails, the on-disk state is unknown (a failed `fsync` cannot be retried safely). The room actor replies with `ErrorCode::Unavailable` (HTTP 503, `Retry-After: 1`), closes its mailbox and terminates. If the record was already synced and only sealing the segment afterwards fails, the commit is acknowledged normally and the actor then terminates the same way. In both cases commands already queued behind it are dropped, so their callers get `Unavailable` instead of hanging; a request that finds the mailbox already closed was never taken, and `RoomManager` sends it to the respawned actor. The next request makes `RoomManager` wait for the old actor to release the room's files and respawn it from disk. If the record did reach disk, deduplication recognizes it, so a retry with the same `MutationId` receives a `CommitAck` with the sequence that was written.
   * Sequential I/O enables high-speed streaming during `/sync`.
   * **`active.wal` is only accessed through its locked handle:** the handle that appends to `active.wal` holds its exclusive lock (`fs2`, which is advisory on Unix but mandatory on Windows, where any other handle fails to read the file). Recovery reads it through that handle when it opens it, and `/sync` reads that reach `active.wal` (for example after the RAM TTL evicted the operations) read through it too; every append first positions the handle at the end of the valid records. The handle is closed before `active.wal` is renamed into a sealed segment.
3. **Tier 3 (Cold Disk Log - Compressed `.wal.zst`):**
   * As segments age past the Warm retention threshold, a background task compresses older `.wal` files into `.wal.zst` segments using Zstandard (isolated in `spawn_blocking`).
   * Allows rooms to retain historical deltas with minimal disk consumption.
   * The compressed segment is written to a temporary file (`segment_{start}_{end}.wal.zst.tmp`), synced and renamed into place, and the directory is synced before the warm segment is deleted (and again after the deletion), so a power loss never persists the deletion without the replacement. Opening the log removes what an interrupted compression leaves behind: temporary files (`segment_*.tmp`) and a cold segment whose warm original still exists (the warm segment is kept and compressed again later), syncing the directory afterwards.
4. **Tier 4 (Eviction & Compaction Boundary - Dual Mode):**
   * **Proactive Cursor-Driven Pruning (`prune_older_than`):** In active rooms, once all registered members confirm having processed up to sequence $S$, segments with `end_seq < S` are immediately purged from disk, reclaiming physical space without waiting for arbitrary TTLs.
   * **Client Lifecycle States (`Connected`, `Disconnected`, `Dormant`, `Bootstrapping`), derived from the cursor:** Every activity of a registered client (heartbeat, sync, ack, commit, including a deduplicated retry) goes through a single entry point, `ClientLeaseTracker::observe(client, reported_cursor, tail_seq)`, which refreshes the lease and recomputes the state from the client's cursor (the stored cursor, moved forward to the reported one; a cursor never moves backwards). `observe` never adds an unregistered client to the roster. Only the fast maintenance tick (every second, see *Maintenance Ticks*) moves clients to `Disconnected` or `Dormant`.
     - **`Connected`:** Active, with a cursor inside the retained log ($\text{cursor} \ge \text{tail\_seq} - 1$); the activity also advances its cursor. If all registered clients are `Connected` and have acknowledged sequence $S$, segments older than $S$ are pruned immediately.
     - **`Bootstrapping`:** Active, but its cursor is behind the retained log ($\text{cursor} < \text{tail\_seq} - 1$): a client registering in that position, or any client whose activity shows it fell behind. Its cursor is not moved, the operation that carried the cursor (if any) is rejected with `BehindCompaction`, and the room asks for a snapshot (see *Snapshot Demand*). An operation can also be rejected with `BehindCompaction` while the client stays `Connected`: when the cursor it carries is stale but the client's stored cursor is still inside the log (for example a commit sent before the client's own ack pruned the log). Such a client needs no snapshot, and the room does not ask for one. `Bootstrapping` clients hold a lease but are excluded from `min_connected_ack_seq`, so they never block disk compaction for active peers. A `Bootstrapping` client becomes `Connected` with its first operation that carries a cursor inside the log (sync, ack or commit, for example after restoring a snapshot).
     - **`Disconnected`:** The lease of a `Connected` or `Bootstrapping` client expired without activity (`lease_timeout_secs`, default 90 s; like every setting of the [lifecycle policy](#53-configurable-lifecycle-policy-roomlifecyclepolicy), a server default that a room can override). While its cursor remains within the log preserved on disk it blocks proactive pruning, since it can still catch up with a standard `/sync`.
     - **`Dormant`:** Inactive and behind the log: on the tick, a `Disconnected` client whose cursor fell behind `tail_seq - 1` becomes `Dormant`. Optionally (`dormant_after_secs`, unset by default; 0 is rejected) a `Disconnected` client also becomes `Dormant` after that much inactivity, even with a cursor inside the log. `Dormant` clients are excluded from log retention calculations (`min_connected_ack_seq`). Note that with `dormant_after_secs` unset (the default) an abandoned client that never deregistered stays `Disconnected` and blocks proactive cursor-driven pruning until TTL or quota compaction moves `tail_seq` past its cursor; only then does it become `Dormant` and stop holding the log back. Setting `dormant_after_secs` releases such clients earlier, at the cost of sending them to a snapshot if the log is pruned meanwhile. Inactivity is counted from the client's last activity, also across restarts of the room actor (for example a shutdown for inactivity): the roster stores it as wall-clock time (see *Client Roster Persistence*). There is no gate on the state itself: when a `Dormant` client comes back, its cursor decides whether it is `Connected` (and its operations succeed) or `Bootstrapping`.
   * **Accurate Physical `tail_seq` Computation:** On open and after every pruning pass, the server computes `tail_seq` strictly from the oldest physically retained operation on disk: the first Cold segment, else the first sealed Warm segment, else the start of `active.wal`. Every operation is written to disk before entering RAM, so the Hot Buffer never defines retention, and RAM TTL eviction never causes spurious `BehindCompaction` rejections. When nothing is retained, `tail_seq = head_seq + 1`, so a cursor at `head_seq - 1` is rejected instead of silently missing the last operation. A gap found while reading a range the log claims to retain is reported as `BehindCompaction`, and so is a range that no tier can serve at all (for example a segment missing at the end of the disk tiers): a read below `head_seq` never returns an empty batch.
   * **Damaged Segments:** `head_seq` comes from the segment names (sequences in a name may have been delivered, so they are never reused), even when a sealed segment holds fewer operations than its name claims. The Hot Buffer is only rehydrated with a contiguous run that ends exactly at `head_seq`; otherwise it starts empty, so reads go to disk and the missing operations surface as a gap, while new commits continue from `head_seq`. A sealed segment that fails to decode (corruption that is not a torn tail) does not prevent opening the room: reading backwards stops there and older operations and mutation IDs are not loaded. Reading it later is reported as `BehindCompaction` (logged as an error with the segment's path), which makes the room ask for a snapshot. Corruption in `active.wal` other than a torn tail still fails the open.
   * **Client Roster Persistence (`meta_clients_{room_id}.json`):** Registration and deregistration are written immediately, and the roster file is written before the change is applied in memory: if the write fails the request fails and the client stays as it was (unregistered, registered with its previous entry, or still registered). Cursor and lease-state changes (ACKs, cursors reported by syncs and commits, state changes from any activity, timeouts) update memory and mark the roster dirty; the room actor writes it on its fast maintenance tick (every second), when it stops (shutdown, inactivity or failure; not after a panic, when its memory cannot be trusted), and before any proactive prune that deletes segments, so the roster on disk never falls behind the retained log. A crash therefore loses at most ~1 s of cursor progress, which only makes the server retain more log. A roster that cannot be parsed at open is discarded with a warning: the room starts with an empty roster, clients register again, and proactive pruning stays stopped until they do. The file is a JSON object `{ "clients": [...], "snapshot_demand": { "renewed_at_unix_ms": ... } | null }`; files in the earlier format (a bare array of clients) still load and are rewritten in the new format on the next save. Each client entry also stores `last_seen_unix_ms`, the wall-clock time of its last activity, so that lease and dormancy timeouts keep counting when the room reopens (an `Instant` does not survive the actor). It is computed from the in-memory activity whenever the roster is written, and activity alone does not make the roster dirty (no write per heartbeat): the stored value is refreshed by the next write, and the actor also writes the roster when it stops if any client was active since the last write. When the room opens, a client's inactivity is restored from it; a time in the future (the wall clock moved backwards) or a missing field (an older roster) counts as active at open time. After a crash, the roster may predate the client's latest activity, so the restored inactivity can be longer than the real one: the client may become `Disconnected` early (it reconnects with its next request), or `Dormant` early when `dormant_after_secs` is set. An invalid client entry only drops that client, and an invalid `snapshot_demand` only drops the demand (with a warning), never the clients.
   * **Atomic Server Metadata:** `meta_room.json`, the client roster and the schema files (`schemas/{schema_id}.json`) are always replaced through a temporary file that is synced, renamed over the destination, followed by a sync of the parent directory. Leftover `.tmp` files from an interrupted write are removed on load. Directories created by the server (room, segments, schemas) are synced into their parent directory. An unreadable `meta_room.json` or schema file makes loading fail rather than serving a room with an unknown schema; so does a `meta_room.json` whose lifecycle overrides are invalid (unknown fields or values out of range).
   * **Durable Sequence Floor (`log_meta.json`):** Before any segment is deleted, the highest pruned sequence is written atomically to `log_meta.json`. Recovery takes the maximum of that value and the retained segments, so a restart after every segment was pruned never reuses sequence numbers already delivered to clients.
   * **Segment Index:** `TieredLog` keeps an in-memory index of its sealed segments (sequence range, tier, size, and when the segment entered its tier), plus the start, end and size of `active.wal`. It is built with a single listing of the segments directory when the log opens and updated by the log itself on every rotation, compression and prune. The listing finds the segments; each one's size and modification time (its age after a reopen) are then read from the file itself (`fs::metadata`), because on Windows the size a directory listing reports can lag behind the file's. Serving deltas, maintenance and pruning never list the directory.
   * **Maintenance Ticks:** The room actor runs two periodic passes. The fast tick (every second) only touches memory, plus the roster file when it changed: lease timeouts and state transitions, snapshot signals (demand expiry, uploader designation, snapshot announcements), roster persistence, and the inactivity check. The slow tick (every 30 seconds) does the disk maintenance of the log from the segment index: compression of aged warm segments, the RAM TTL window, cold TTL and quota pruning, and a backup pass of the cursor-driven pruning, which also runs on every Ack (a floor can move without an Ack: cursors reported by commits, clients becoming `Dormant`). So a sealed segment is compressed, and an expired one pruned, up to 30 s after its TTL. A room that shuts down for inactivity runs one disk maintenance pass on the way out (after handling the commands still queued), so a room whose `idle_timeout_secs` is shorter than the slow tick still compresses, expires and enforces its quota across its open/idle cycles. A failed compression does not stop the pass: the TTL, quota and RAM window still apply, and once the cold segment is in place (renamed, synced and verified) the index points at it even if removing the warm segment then fails; that warm file is resolved the next time the log opens. Both periods are internal constants.
   * **Room Log Lock:** Before opening touches any file (the cleanup of `log_meta.json.tmp` and of compression leftovers, the reads of the log), it takes an exclusive lock on `log.lock` in the room directory, held for as long as the log is open; a second opener, in this or another process, fails with `RoomLocked` and changes nothing. The lock lives on the open handle and the file is never read, so it works the same on Windows, where locks are mandatory. The lock on `active.wal` is not enough on its own: that file does not exist between a rotation and the next append. `RoomManager` respawns a room only after the previous actor has finished and dropped its log.
   * **Opening a Room:** Opening (or reopening, which the inactivity shutdown makes frequent) does not read the whole retained log. `head_seq` comes from the segment names, `active.wal` and `log_meta.json`; the log is then read backwards from `active.wal` and the newest segment only until it holds the last `ram_max_ops` operations (for the Hot Buffer) and the last `dedup_lru_capacity` distinct mutation IDs (for deduplication; at least one, as the cache holds at least one), and both are hydrated oldest first, so the deduplication cache keeps the order of recency. A mutation ID that appears twice (appended again after it left the window) counts once, with its newest sequence. The Hot Buffer is rehydrated with the contiguous run of operations ending at `head_seq` (see *Damaged Segments*). The cost of opening a room therefore depends on these two settings, not on how much history it retains.
   * **Blocking I/O in the Actor:** Room actors are Tokio tasks, and their file I/O is synchronous: the append of each commit with its `fsync`, `log_meta.json` and roster writes, the reads of `/sync` that reach the disk tiers (including the decompression of cold segments), pruning, and opening the room. All of it runs through one helper (`blocking_io`) that uses `tokio::task::block_in_place`, which hands the worker's other tasks (for example other rooms) to another thread while the actor blocks. On a current-thread runtime, where `block_in_place` is not allowed, the work runs in place. Compression of warm segments runs on the blocking pool (`spawn_blocking`).
   * **Snapshot Retention Anchor (*Ancla de Retención*):** To protect onboarding clients against race conditions where active peers continue appending commits and pruning logs while a snapshot is being downloaded, the server anchors proactive pruning to:
     $$\text{retention\_floor} = \min(\text{min\_connected\_ack}, \text{active\_snapshot\_seq})$$
     As long as an active snapshot at sequence $S$ is published in `SnapshotRelay`, operations $(S, \text{head\_seq}]$ are preserved on disk. The relay only accepts snapshots inside the retained range ($\text{tail\_seq} - 1 \le S \le \text{head\_seq}$); if TTL or quota compaction later moves `tail_seq` past $S + 1$, the snapshot is no longer *usable* ($\text{tail\_seq} - 1 \le S \le \text{head\_seq}$ fails) and no longer anchors pruning. When the bootstrapping client finishes applying snapshot $S$ and fetches deltas or ACKs $\ge S$, it is automatically promoted to `Connected`.
   * **Snapshot Demand and Uploader Designation:** The room actor tracks whether the room *needs a snapshot*. The demand turns on (or is renewed) when there is no usable snapshot and a client registers as `Bootstrapping`, or any activity (an operation rejected with `BehindCompaction`, a heartbeat, a deduplicated commit) leaves a client `Bootstrapping`. A `BehindCompaction` answer to a client whose stored cursor is still inside the log does not turn it on. The exception is a sync whose range starts inside the retained log but cannot be served because of a gap: no client can catch up through that range, so that answer always turns the demand on. It turns off when a usable snapshot appears in the relay (detected on the fast maintenance tick) or when `snapshot_demand_ttl_secs` (lifecycle policy, default 7 days; below 60 s is rejected, since the demand would flap) passes without a renewal. The demand is stored in the client roster as the wall-clock time of its last renewal (an `Instant` does not survive a restart) and flushed on the fast maintenance tick like cursors. Turning the demand on or off marks the roster dirty; a renewal only does once the stored time is older than `min(TTL / 100, 1 hour)`, so a client waiting for a snapshot does not cause a roster write per heartbeat. As a consequence, after a restart a restored demand may expire up to that granularity earlier than it would have otherwise. When the room reopens (after a restart or after its actor stopped), a persisted demand is restored unless a usable snapshot exists or its last renewal is older than the TTL; a renewal time in the future (the wall clock moved backwards) counts as renewed at open time, and is stored as such, so it cannot keep the demand alive indefinitely. While the demand is on, the actor designates exactly one uploader among the `Connected` clients (never a `Bootstrapping`, `Disconnected` or `Dormant` one): the highest cursor wins, ties go to the most recent activity, then to the lowest client id. If no upload starts within 60 s of the designation, or the designee stops being `Connected`, another client is designated and the previous one is excluded for the rest of the episode (once every candidate has been excluded, the exclusions are reset). While any upload for the room is in progress in the relay, the designation never changes. With no candidate, the demand stays on without a designee until a client becomes `Connected`. The designation (designee, exclusions, 60 s deadline) lives in memory only: after the room reopens it is recomputed from the roster. Only the designee receives `snapshot_wanted: true` in its `HeartbeatAck`, `SyncBatch` and `CommitAck`; each new designation is also broadcast as the SSE event `snapshot_wanted`, and each new usable snapshot as `snapshot_available`.
   * **TTL & Quota Compaction:** Historical operations exceeding `cold_disk_ttl` or the room disk quota (`max_room_disk_bytes`) are automatically pruned, on the slow maintenance tick. The oldest cold segments are deleted while they are past the TTL (counted from their compression) or the log is over the quota; pruning stops at the first segment that is kept, so the retained range never has holes. The log's size (sealed segments plus `active.wal`) is tracked incrementally by the segment index, not measured on disk. The server tracks the oldest available sequence (`tail_seq`). Any sync request with `last_ack_seq < tail_seq - 1` receives `BehindCompaction`, recovering state via full base snapshot transfer from an active client (via server relay or P2P).

### 5.3. Configurable Lifecycle Policy (`RoomLifecyclePolicy`)
Every tier threshold, the room disk quota, the client lifecycle timeouts and the inactivity shutdown form the room's lifecycle policy. The server sets a default for each setting (a TOML field, which the environment variable listed next to it overrides; their names differ, see the table), validated at startup, and a room can override any of them when it is created:

```rust
pub struct RoomLifecyclePolicy {
    pub ram_max_ops: usize,                  // operations kept in RAM before the active segment is sealed
    pub ram_ttl: Duration,                   // time-to-live of operations in RAM
    pub warm_disk_ttl: Duration,             // age at which a sealed segment is compressed
    pub cold_disk_ttl: Duration,             // age at which a compressed segment is pruned
    pub max_room_disk_bytes: u64,            // disk space of the room's log before early pruning
    pub lease_timeout: Duration,             // client inactivity before Disconnected
    pub dormant_after: Option<Duration>,     // Disconnected inactivity before Dormant (None: only when behind the log)
    pub snapshot_demand_ttl: Duration,       // lifetime of an unrenewed snapshot demand
    pub idle_timeout: Option<Duration>,      // room inactivity before its actor shuts down (None: never)
}
```

| Setting (TOML / JSON) | Environment variable | Default | Accepted |
|---|---|---|---|
| `ram_max_ops` | `ZEMDB_RAM_MAX_OPS` | 1,000 | 1 – 100,000 |
| `ram_ttl_secs` | `ZEMDB_RAM_TTL_SECS` | 300 (5 min) | 1 s – 10 years |
| `warm_disk_ttl_secs` | `ZEMDB_WARM_TTL_SECS` | 86,400 (24 h) | 0 – 10 years (0: compress when sealed) |
| `cold_disk_ttl_secs` | `ZEMDB_COLD_TTL_SECS` | 2,592,000 (30 days) | 0 – 10 years (0: prune when compressed) |
| `max_room_disk_bytes` | `ZEMDB_ROOM_MAX_DISK_BYTES` | 524,288,000 (500 MiB) | at least 1 MiB |
| `lease_timeout_secs` | `ZEMDB_LEASE_TIMEOUT_SECS` | 90 | 1 s – 10 years |
| `dormant_after_secs` | `ZEMDB_DORMANT_AFTER_SECS` | unset | 1 s – 10 years when set |
| `snapshot_demand_ttl_secs` | `ZEMDB_SNAPSHOT_DEMAND_TTL_SECS` | 604,800 (7 days) | 60 s – 10 years |
| `idle_timeout_secs` | `ZEMDB_ROOM_IDLE_TIMEOUT_SECS` | 600 (10 min) | 0 – 10 years (0: never) |

* **Server defaults:** An environment variable overrides the TOML field. An empty variable (`ZEMDB_X=`, as templates such as `${X:-}` produce) counts as unset. A non-empty variable that cannot be parsed (not an unsigned integer, not valid Unicode, out of the type's range), or a value outside its accepted range, makes the server refuse to start with an error naming the setting and its variable. The 10-year ceiling keeps every deadline computed from a setting far from overflowing. The same strict parsing applies to the other numeric variables (`ZEMDB_PORT`, `ZEMDB_DEDUP_LRU_CAPACITY`, `ZEMDB_SNAPSHOT_TTL_SECS`, `ZEMDB_MAX_SNAPSHOT_BYTES`, and the HTTP limits of [7.3](#73-http-edge-transport-and-limits)).
* **Per-room overrides:** `POST /admin/rooms` accepts an optional `lifecycle` object with any of the settings above (durations as integer seconds, `*_secs`). Unknown fields and values outside the accepted ranges are rejected with JSON `BadRequest` (400) before anything is written. The room stores only its overrides, in `meta_room.json` (`"lifecycle": {...}`); a file without them has none. Whenever the room actor is spawned (creation, the first request after a restart, a respawn after a failure, a panic or an inactivity shutdown) its effective policy is computed again as the server defaults overlaid with the stored overrides, so a setting that is not overridden follows the current server default. No rule relates two settings, so valid overrides on valid defaults always give a valid policy. An override can set `dormant_after_secs` but not clear a server default; `idle_timeout_secs: 0` disables the inactivity shutdown for the room. Changing the overrides of an existing room is not supported yet.
* **Global settings:** The snapshot relay's `snapshot_ttl_secs` and `max_snapshot_bytes`, and `dedup_lru_capacity`, apply to every room.

This ensures the system is adaptable across diverse deployment profiles, from resource-constrained edge gateways to large-scale enterprise coordination hubs.

### 5.4. Room Actor Lifecycle: Inactivity and Panics
* **Spawning:** `RoomManager` spawns a room's actor on the first request that needs it, under a per-room spawn lock. The lock's map entry is removed when it is released, but only by its holder and only if no other task holds a reference to it (one waiting for it), so concurrent callers always share one mutex and the map does not grow with every room ever opened. When an actor stops, its task reports how it ended once the actor has released the room's files, and removes its own entry from the manager; a request arriving in the meantime waits for that report before respawning the room from disk.
* **Inactivity shutdown:** On each fast maintenance tick, an actor that received no command for `idle_timeout_secs`, has no SSE subscriber and no snapshot upload in progress in the relay shuts down: it closes its mailbox (so `RoomManager` respawns the room for the next request), handles every command already queued as usual, persists the roster and exits, releasing memory, files and the log lock. A request that finds the mailbox closed was never taken, so `RoomManager` sends it to the respawned actor; no request is lost or answered with an error because of the shutdown. The only exception is an SSE subscription queued during the shutdown, which the actor refuses with `Unavailable` (the stream would end at once) and the SSE handler retries against the reopened room. The snapshot demand is persisted in the roster, so it survives; the designated uploader is recomputed on reopening. Before exiting, the actor runs one disk maintenance pass (compression, TTL, quota). A room that is shut down runs no further maintenance until a request reopens it.
* **Panics:** The actor's loop runs inside `catch_unwind`. A panic ends the actor, which is reported as terminated by a panic: every command still queued is answered with `Unavailable` (HTTP 503, retryable), and the command being handled, whose reply was lost, gets `Internal` (HTTP 500, not retried: the same request could panic again). `RoomManager` tells the two cases apart when a reply is dropped by waiting (at most 1 s) for the actor to finish: after a panic the request is `Internal`; after a deliberate stop (a failed log write, a shutdown) it is `Unavailable`. The roster is not persisted after a panic. The next request respawns the room from disk as usual.

## 6. Onboarding, Handshake & Stateless Authentication

Because the server does not store the full persistent historical state and must remain completely decoupled from application user/password databases:

1. **Stateless Ticket Authentication & Registration Handshake:**
   * The application backend authenticates the end-user (OAuth, email/password, etc.) and issues a signed, time-bounded ticket:
     `auth_token` signed with the shared cluster secret (`ZEMDB_AUTH_SECRET`). Format: `v1.<base64url(client_id)>.<base64url(room_id)>.<expires_at>.<hex_signature>`. The IDs are base64url-encoded (an alphabet without `.`), so the token is unambiguous for any valid ID. The signature is keyed BLAKE3 over the length-prefixed claims `(client_id, room_id, expires_at)`, with a signing key derived from the secret via `blake3::derive_key` under a dedicated context string, so the key is never shared with other uses of the secret. `expires_at` must be in canonical decimal form (no sign, no leading zeros), so each claim set has exactly one valid token string. The version prefix allows the format to evolve; tokens in any other format are rejected.
   * The client connects and issues `ClientMessage::RegisterClient { correlation_id, room_id, client_id, auth_token, current_seq: Option<SequenceNumber> }`.
   * The server validates the cryptographic signature in microsecond CPU time without querying any database or storing user passwords.
   * The server responds with `ServerMessage::Registered { head_seq, tail_seq, active_snapshot_seq: Option<SequenceNumber>, schema_id, schema }`, delivering room boundary coordinates and the full schema in 1 RTT. `active_snapshot_seq` is only reported if the snapshot is usable ($\text{tail\_seq} - 1 \le S \le \text{head\_seq}$), as in `HeartbeatAck`. A `current_seq` above `head_seq` was never delivered by the room and is rejected with `InvalidSequence` (HTTP 400) without touching the roster.

2. **Client State & Synchronization Path Determination:**
   * **Direct Delta Catch-up (`Connected`):** If its `current_seq >= tail_seq - 1` (or the room is unpruned), the client enters `ClientState::Connected`. It immediately queries `/sync` starting from `current_seq` to catch up with all recent deltas.
   * **Snapshot Bootstrapping (`Bootstrapping`):** If the client is brand new or reconnecting with `current_seq < tail_seq - 1` (or `None` in a room where `tail_seq > 1`), it enters `ClientState::Bootstrapping`. The client is excluded from log retention tracking, preventing it from blocking active members, and if the relay holds no usable snapshot the room turns its snapshot demand on.

3. **Snapshot Delivery & Retention Anchor:**
   * If an active base snapshot is already uploaded to `SnapshotRelay` (indicated by `active_snapshot_seq: Some(S)`), the client downloads it with the chunked protocol (`POST /rooms/:id/snapshot/chunk`).
   * If no usable snapshot exists on the relay, the room turns its snapshot demand on and designates one connected peer (see *Snapshot Demand and Uploader Designation*). The bootstrapping client keeps heart-beating; its `HeartbeatAck` reports `active_snapshot_seq` as soon as a usable snapshot exists (foreground clients also get the SSE event `snapshot_available`).
   * The designated peer, told by `snapshot_wanted: true` in its replies (or prompted by the SSE event `snapshot_wanted` to send a heartbeat), generates an immutable Zstandard snapshot at sequence $S$ and uploads it, in one request (`POST /rooms/:id/snapshot/upload` with header `x-snapshot-head-seq: S` and the raw snapshot as body, up to the request body limit; acknowledged with the binary frame `ServerMessage::SnapshotStaged { room_id, snapshot_head_seq, snapshot_hash }`) or in chunks (`POST /rooms/:id/snapshot/upload-chunk`).
   * **Retention Anchor Protection:** While this snapshot remains active on the server relay, the room actor anchors its proactive pruning floor to $\min(\text{min\_connected\_ack}, S)$. This guarantees that all operations $(S, \text{head\_seq}]$ are preserved in the log.
   * Multiple clients can onboard simultaneously against the same snapshot without race conditions.

4. **Snapshot Restoration & Seamless Promotion:**
   * The bootstrapping client restores the snapshot locally via `StorageEngine::apply_snapshot`, setting its local sequence to $S$.
   * It then issues `ClientMessage::Sync { from_seq: S, .. }` or commits a mutation.
   * Upon processing the deltas $(S, \dots]$, the client's ACK or sync request automatically promotes it from `Bootstrapping` to `Connected`, and normal cursor tracking resumes.

### Multipart Chunked Snapshot Transfer Protocol (> 16 MB)

When database rooms grow large such that compressed snapshots exceed the strict DoS envelope (`MAX_MESSAGE_SIZE = 16 MB`), state transfer is partitioned into framed chunks:
1. **Anchored Chunk Requests:** The bootstrapping client issues `ClientMessage::RequestSnapshotChunk { correlation_id, room_id, chunk_index, chunk_size, snapshot_hash }`. The first request of a download (chunk 0) carries `snapshot_hash: None` and gets the room's active snapshot; every following request must carry the `snapshot_hash` returned by the first reply (a request for a later chunk without it is `BadRequest`, 400), anchoring the whole download to that snapshot. The unanchored first request also asks the room actor for the retained log range: a snapshot that fell below it ($S < \text{tail\_seq} - 1$, so the client could not catch up from the log) is dropped and its file deleted, and the answer is `RoomNotFound` (404), as when no snapshot was ever staged. The server clamps `chunk_size` to 64 KiB–4 MiB; the client learns the size actually used from `total_chunks` and `total_bytes`.
2. **Chunk Streaming:** The relay answers `ServerMessage::SnapshotChunk { correlation_id, room_id, snapshot_head_seq, chunk_index, total_chunks, total_bytes, snapshot_hash, data }`, reading the chunk from the snapshot file.
3. **Superseded Snapshots:** If the anchored snapshot is no longer the active one (a newer snapshot replaced it, or it expired), including when reading its file fails because it was replaced during the read, the relay answers `ErrorCode::SnapshotSuperseded` (HTTP 409). The client discards the chunks received so far and restarts from chunk 0 without `snapshot_hash`. Anchoring by hash rather than by sequence also catches a replacement with the same sequence.
4. **Cryptographic Integrity & Atomic Reconstruction:** All chunks `0..total_chunks` are assembled in a temporary staging buffer. The client validates the assembled byte stream against `snapshot_hash` using BLAKE3 (`ServerMessage::compute_snapshot_hash`), immediately rejecting corrupted transfers before decompression. If verified, it applies the snapshot in a single atomic transaction via `StorageEngine::apply_snapshot`.
5. **Resumed Delta Catch-up:** The client sets its local cursor to `snapshot_head_seq` and seamlessly queries `/sync` starting from `snapshot_head_seq + 1`.

Uploads in chunks use `ClientMessage::UploadSnapshotChunk { snapshot_head_seq, chunk_index, total_chunks, total_bytes, snapshot_hash, data }`, acknowledged with `ServerMessage::SnapshotUploadChunkAck { staged }` (`staged: true` on the chunk that completes the upload):
* Every chunk except the last has exactly `ceil(total_bytes / total_chunks)` bytes; the last has the exact remainder. Chunks are at most 4 MiB and, when there is more than one, at least 64 KiB (a smaller snapshot is uploaded in fewer chunks). `total_bytes` is at most `max_snapshot_bytes`. Chunks may arrive in any order; resending a chunk overwrites it. Resending a chunk of an upload that already completed (same sequence and hash as the active snapshot, for example after a lost acknowledgment) is acknowledged again with `staged: true`; likewise, repeating a single-request upload of the active snapshot returns success.
* A room has at most one upload in progress, and it records who started it (the snapshot worker, authenticated with the admin secret, or a member's client id). A chunk for a higher sequence replaces the current upload (its partial file is deleted). A chunk for the same sequence with different parameters replaces it only if it comes from the snapshot worker or from the member who started it (to restart its own upload); otherwise, and for a lower sequence, it is rejected with `SnapshotSuperseded` (409). So a member keeping a bogus upload alive cannot block the snapshot worker. An upload that receives no chunk for 2 minutes is discarded.
* When the last chunk arrives, the relay hashes the assembled file with BLAKE3 and rejects it (`BadRequest`) unless it matches `snapshot_hash`.

### Snapshot Relay: Storage, Acceptance and Limits

* **Disk only:** Staged snapshots are never held in memory. The relay keeps their metadata (sequence, size, BLAKE3 hash, path) and serves each download chunk by opening the file, seeking and reading the range on Tokio's blocking pool. Files live in `<data_dir>/snapshots/` as `<room>_<seq>_<blake3>.snap`; partial uploads live in `<data_dir>/snapshots/uploads/`. A snapshot is written to a temporary file, synced, renamed into place and the directories synced; the previous snapshot file of the room is deleted only after that. If any step fails the previous snapshot stays active.
* **Acceptance:** A snapshot at sequence $S$ (single request, or a completed chunked upload) is accepted only if the room exists (`RoomNotFound`, 404, otherwise), $\text{tail\_seq} - 1 \le S \le \text{head\_seq}$ as reported by the room actor (`BadRequest`, 400, otherwise; for chunked uploads checked when the upload starts and again when it completes, since both bounds move), $S$ is strictly greater than the active snapshot's sequence (`SnapshotSuperseded`, 409, otherwise), and the bytes form a `ZMSN` envelope with a valid header and a CRC32 matching the body (`BadRequest` otherwise). Changes to a room's snapshot and upload are serialized per room, so concurrent uploads can neither delete each other's files nor move the active snapshot backwards.
* **What the server does not check:** The relay validates only the envelope header and checksum; it never decompresses the snapshot and has no room state to compare it with. A snapshot can therefore be well-formed and still wrong: the client must validate its structure when applying it (Phase 4), and a malicious room member (or the holder of the admin secret) can still upload a poisoned snapshot within the acceptance rules. Defending against that is out of scope for v0.1.
* **Limits:** `max_snapshot_bytes` (default 512 MiB, `ZEMDB_MAX_SNAPSHOT_BYTES`) bounds every snapshot; it must lie between 1 MiB and 64 GiB, or the server refuses to start. Single-request uploads are additionally bounded by the request body limit (`MAX_FRAME_SIZE`, 16 MiB + 4 bytes; a larger body is a binary `BadRequest` frame with HTTP 413), and at most 2 single-request uploads per room may be in progress at once, since each holds its body in memory while it waits for the room; a third gets `RateLimited` (HTTP 429). Staged snapshots expire after `snapshot_ttl_secs` (default 7 days, `ZEMDB_SNAPSHOT_TTL_SECS`; the defaults target rooms that change slowly, with clients that connect now and then); a background task deletes expired snapshots and idle uploads every 30 s.
* **Startup recovery:** On start the relay deletes every partial upload and, for each room, keeps only the highest-sequence snapshot file that is within the TTL (by modification time) and intact (valid envelope, content hash equal to the one in its name); all other snapshot files are deleted. A file that cannot be read (an I/O error rather than invalid content) is left in place and not served, and no older snapshot of that room is activated in its place, so the active snapshot never moves backwards. Failing to delete a stale file is logged and does not stop the server; the next start retries.
* **Room deletion:** Deleting a room removes its staged snapshot, its upload in progress and their files before the room directory, so a room recreated with the same id never serves the old room's snapshot. An upload that was under way when the room was deleted fails with `RoomNotFound`.
* **Client errors are not server errors:** Malformed chunk parameters, out-of-range indexes, oversized snapshots and unacceptable sequences are `BadRequest` (400); a request for a room without a usable staged snapshot is `RoomNotFound` (404); a superseded snapshot or upload is `SnapshotSuperseded` (409); a body over the size limit is 413 and too many concurrent single-request uploads is `RateLimited` (429). As everywhere in the Data Plane, these are binary `ServerMessage::Error` frames.

## 7. Communication Protocol: Control Plane & Data Plane

The system strictly decouples administrative lifecycle management from high-throughput client synchronization:

### 7.1. Control Plane (Admin REST API - HTTP/JSON)
Dedicated administrative interface intended for application backends, CLI tools, and automated deployment pipelines:
* **Transport:** HTTP REST with JSON payloads, on the same listener and with the same transport as the Data Plane (see [7.3](#73-http-edge-transport-and-limits)).
* **Security:** Authenticated via administrative bearer token (`Authorization: Bearer <ADMIN_SECRET>`).
* **Secret requirements:** On startup the server refuses to run unless both secrets (`ZEMDB_AUTH_SECRET` for client tokens, `ZEMDB_ADMIN_SECRET` for administration and snapshot workers) are set, at least 32 bytes long, different from each other, and different from the built-in development values (which are public in the source code). Error messages name the offending setting but never include the secret.
* **Endpoints:**
  * `POST /admin/schemas`: Declares a schema template identified by `SchemaId`, containing table and column definitions: `{ "schema_id": "...", "schema": { "tables": [ { "table_id": 0, "name": "...", "primary_key": [...], "columns": [...] } ] } }`. Every table needs an explicit `table_id`; a repeated id or name, a missing id or an unknown field is `BadRequest` (400, JSON) and nothing is written. A schema id is declared once: posting an id that is already registered is `SchemaAlreadyExists` (409, JSON) and changes nothing, because a replacement could renumber tables or drop and retype columns under rows already in the rooms' logs. Schemas evolve only through the endpoint below.
  * `GET /admin/schemas/{schema_id}`: Retrieves schema metadata.
  * `POST /admin/schemas/{schema_id}/columns`: Append-only DDL evolution (`Schema::add_column`), enforcing nullable column additions and broadcasting `RoomEvent::SchemaReloaded` across all active rooms. Each running room is sent the registry's current version of the schema (read under the room's spawn lock), not the version this request produced, so concurrent additions reloading in any order still leave every room with the newest schema. The reload runs in its own task, so a request dropped mid-reload still reaches every room; the response waits for it.
  * Schema writes (`POST /admin/schemas` and `.../columns`) are serialized by a single registry-wide lock held from reading the current version to publishing the new one, so two concurrent writes never share a `.tmp` file and a column addition never overwrites another one made concurrently. Reads never wait for it.
  * `POST /admin/rooms`: Provisions an isolated room binding `RoomId` to a `SchemaId`, with optional lifecycle overrides: `{ "room_id": "...", "schema_id": "...", "lifecycle": { "ram_max_ops": 200, "idle_timeout_secs": 0 } }` (any subset of the settings in [5.3](#53-configurable-lifecycle-policy-roomlifecyclepolicy), durations in integer seconds; unknown fields or values out of range are `BadRequest`). Answers 201 with the stored `meta_room.json`: `{ "room_id", "schema_id", "lifecycle": { ...overrides... } }`.
  * `GET /admin/rooms/{room_id}`: Inspects the room: `room_id`, `schema_id`, `head_seq`, `tail_seq`, client counts per lifecycle state, `lifecycle` (the effective policy the running actor uses, every setting present, durations in whole seconds, `dormant_after_secs: null` when unset and `idle_timeout_secs: 0` when the room never shuts down for inactivity) and `lifecycle_overrides` (the room's stored overrides). Verifies room existence passively with `room_exists`, returning HTTP 404 `NotFound` for non-existent rooms without spawning actors or creating directories on disk.
  * `DELETE /admin/rooms/{room_id}`: Archives or purges a room and its WAL.

### 7.2. Data Plane (Client Synchronization Protocol - Binary HTTP)
To prevent the resource exhaustion of thousands of idle persistent connections:
* **Pull-Based Binary HTTP Protocol:**
  * Transport: HTTP/1.1 or HTTP/2 with binary payloads serialized via `bincode`. The server does not terminate TLS: it is deployed behind a reverse proxy that does (see [7.3](#73-http-edge-transport-and-limits)).
  * **Canonical Wire Protocol Framing:** Every network frame is encapsulated in a fixed 4-byte header: Magic bytes `0x5A, 0x4D` (`"ZM"`), Protocol Version `0x01`, and Reserved Flags `0x00`. The protocol version stays `0x01` until the first release; from then on it changes with every incompatible wire change between published releases.
  * **Typed Decode Errors:** `decode_message` validates the header before anything else and reports a typed `DecodeError`: `TooShort` (shorter than the header), `InvalidMagic` (not a ZemDB frame), `UnsupportedVersion { expected, got }` (a ZemDB frame of another version), `TooLarge` (over `MAX_FRAME_SIZE`), `Malformed` (a payload that is not a valid message of the expected type, including invalid identifiers, trailing bytes and rows, keys or update deltas of more than `MAX_COLUMNS` elements) or, only from `decode_client_message`, `TooManyValues` (see *Defensive Bounding*). Because the version is checked first, a frame of another version is always `UnsupportedVersion`, whatever its size or payload. The server answers `UnsupportedVersion` with `ErrorCode::ProtocolVersionMismatch` and every other decode failure with `ErrorCode::BadRequest`, both HTTP 400.
  * **Version Mismatch Rule:** A peer of another version cannot decode the frames of this one, error frames included, so the error frame alone cannot tell it about the mismatch. The rule is therefore: **a response whose header carries the ZemDB magic and another protocol version means a protocol version mismatch, whatever its HTTP status and body.** Clients check it with `peek_version` (or a `DecodeError::UnsupportedVersion` from `decode_message`) before interpreting the status. The rule is about the frames the client reads; what the server reports for a request of another version depends on how far the request gets: `decode_message` reports `UnsupportedVersion` whatever the frame's size, but over HTTP a body over the size limit is rejected with 413 before it is decoded, and authenticated endpoints check the token (401/403) before decoding the body.
  * Wire Efficiency (50%+ Bandwidth Reduction): Replacing string-keyed dictionaries with `CompactRow` and `ColumnUpdate` deltas eliminates column names from the wire, reducing serialized insert/update payloads by 38% to 60%.
  * Multiplexing (HTTP/2): Multiple sync/commit streams share a single underlying TCP connection using explicit correlation identifiers (`CorrelationId`). Over HTTP/1.1 a connection carries one request at a time.
  * Defensive Bounding: Codecs enforce an explicit payload size limit (`MAX_MESSAGE_SIZE`, 16 MiB) to prevent denial-of-service memory exhaustion attacks. A frame is the payload plus the header, so the largest frame is `MAX_FRAME_SIZE` = `MAX_MESSAGE_SIZE + 4` bytes: `encode_message` produces frames up to that size and `decode_message` accepts exactly the same. The server's request body limit is `MAX_FRAME_SIZE` too, except for `/register` (see [7.3](#73-http-edge-transport-and-limits)). The byte limit does not bound the memory a decode reserves, because a `Value` takes 24 bytes in memory and as little as 1 byte on the wire (`Null`), so two more limits apply when decoding: a `CompactRow`, a `PrimaryKey` or the deltas of an `Update` hold at most `MAX_COLUMNS` (65,535) elements, checked as they are decoded (a declared length above it is rejected before decoding anything, and the preallocation is capped regardless of the declared length); and the server decodes every request with `decode_client_message`, which materializes at most `MAX_MESSAGE_VALUES` (2^20) values per message, about 24 MiB, and fails with `TooManyValues` past it. Responses decoded by clients (`decode_message`) have no value budget, since a `SyncBatch` of 16 MiB can legitimately carry more values.
  * **Size of a single mutation:** Every accepted operation fits alone both in a WAL record (bincode with fixed-width integers, payload up to `MAX_MESSAGE_SIZE`) and in a response frame (its wire encoding at most `MAX_RESPONSE_OPS_BYTES` = `MAX_MESSAGE_SIZE - RESPONSE_ENVELOPE_ALLOWANCE`, where the allowance is the largest encoding of the other fields of a `CommitAck` or `SyncBatch`, with maximal identifiers). Fixed-width integers make the WAL record larger than the wire encoding (a small integer takes 2 bytes on the wire and 12 in the log), so a commit whose request frame is legal can still be too large. `check_operation_size` (in `zemdb-core`, usable by clients before sending) applies both limits; the room actor runs it before assigning a sequence number and rejects a commit that fails it with `BadRequest` (400), with no side effects: the room keeps running and nothing is sequenced, logged or broadcast.
* **Universal Security & Defense-in-Depth (edge extractors, `api/extract.rs`):**
  * **Edge Validation Extractors:** Untrusted input is parsed once, by Axum extractors, before any handler code runs:
    * `RoomPath` parses the `:room_id` path segment into a `RoomId` (invalid → binary `ErrorCode::BadRequest`, HTTP 400).
    * `AuthenticatedRoom { room_id, client_id }` adds cryptographic authentication: all operational Data Plane endpoints (`/commit`, `/sync`, `/ack`, `/heartbeat`, `/schema`, `/deregister`, `/events`) require a client token in `Authorization: Bearer <token>`, validly signed, unexpired and issued for the path room. A missing, malformed, wrongly signed or expired token is rejected with a binary `ErrorCode::Unauthorized` frame (HTTP 401: get a new token); a valid token issued for another room with `ErrorCode::Forbidden` (HTTP 403: permanent for that token). Tokens in the URL are not accepted on these endpoints (they would end up in access logs); the only exception is `/events`, through `EventStreamAuth`, which also accepts `?token=<token>` because browser `EventSource` connections cannot set headers.
    * `RelayAuth` does the same for the snapshot relay endpoints (`/snapshot/upload`, `/snapshot/chunk`, `/snapshot/upload-chunk`), which additionally accept the admin secret as Bearer token (automated snapshot workers). `EventStreamAuth` applies the same rules (and codes) to `/events`.
    * `BinaryMessage` decodes the request body as a `ClientMessage` with `decode_client_message`, within the router's body limit (`MAX_FRAME_SIZE`); a frame of another protocol version is a binary `ErrorCode::ProtocolVersionMismatch` and any other decode failure, including an invalid identifier inside the payload, a binary `ErrorCode::BadRequest` (both HTTP 400); a body that cannot be read is `BadRequest` with its own status (413 when too large), or `RequestTimeout` (408) when it does not arrive in time (see [7.3](#73-http-edge-transport-and-limits)). The error frame carries the path room id when it is valid.
    * **The Data Plane is fully binary:** every response of `/rooms/...`, success or error, is a protocol frame (`application/octet-stream`), including requests that match no route: an unknown path gets a `BadRequest` frame with HTTP 404, and a known path with a method it does not accept a `BadRequest` frame with HTTP 405. This includes authentication failures, the snapshot relay (the single-request upload is acknowledged with `ServerMessage::SnapshotStaged`) and SSE errors, before or after authentication (for example a room that does not exist, or an actor that stopped or timed out while subscribing); once subscribed, the SSE stream itself is `text/event-stream`. Only the Control Plane (`/admin/...`) answers JSON.
    * Admin endpoints use `AdminPath<T>` (validated `RoomId`/`SchemaId` path parameters) and `AdminJson<T>` (JSON bodies), whose rejections are JSON `ErrorCode::BadRequest` responses: HTTP 400, or 413/415 for an oversized body or a missing JSON content type. A body that does not arrive in time is JSON `ErrorCode::RequestTimeout` (408).
    * `register` carries its token inside the `RegisterClient` message, so it uses `RoomPath` + `RegisterMessage` and verifies the token bound to the message's client and room. Since nothing is authenticated before the body is read, `RegisterMessage` reads the message kind from the variant tag that follows the frame header (`peek_client_message_kind`) and rejects any other kind with `BadRequest` (400, "Expected RegisterClient message") without decoding the rest of the frame.
  * **Constant-Time Verification (`subtle::ConstantTimeEq`):** Token keyed-BLAKE3 signatures and admin secrets are verified using constant-time byte comparisons, eliminating side-channel timing attack vulnerabilities (`M-04`).
  * **Zero Backdoors:** Development bypasses (`"dev-token"`) are eliminated; all incoming tokens require valid cryptographic signatures issued with the configured secret (`M-05`).
  * **3-Way Route and Token Validation (`M-07`):** Before actor dispatch:
    1. The `room_id` in the URL path must match the `room_id` claim in the verified token (checked by the extractor; mismatch → `ErrorCode::Forbidden`, HTTP 403).
    2. The `room_id` in the binary `ClientMessage` payload must match the URL path (checked by the handler; mismatch → `ErrorCode::BadRequest`, HTTP 400).
    3. The `client_id` in the binary `ClientMessage` payload must match the `client_id` claim in the verified token (checked by the handler; mismatch → `ErrorCode::Forbidden`, HTTP 403).
    This prevents cross-room spoofing and client impersonation. `register` applies the same split to the token inside `RegisterClient`: invalid or expired → 401 `Unauthorized`; validly signed but issued for another client or room → 403 `Forbidden`.
  * **Actor-Level Lease Validation (`C-03`):** Even with a cryptographically valid token, `RoomActor` validates that the requesting client possesses an active registration in `ClientLeaseTracker` before processing `Commit`, `Sync`, `Ack`, or `Heartbeat`. Unregistered clients (never registered, or deregistered) are rejected with `ErrorCode::ClientNotRegistered` (HTTP 409): the client must register again.
* **Core Interaction Contracts:**
  * **Handshake & Schema Delivery (`RegisterClient` -> `Registered`):** Client presents `auth_token` and optional `current_seq`, receiving current `head_seq`, `tail_seq`, `active_snapshot_seq` (only a usable snapshot), `schema_id`, and `Schema` in 1 RTT. `current_seq > head_seq` is `InvalidSequence`.
  * **On-Demand Schema Refresh (`GetSchema` -> `Schema`):** Allows clients to refresh schema definitions during active DDL evolution without reconnecting (`POST /rooms/{room_id}/schema` authenticated via `AuthenticatedRoom`).
  * **Mutation Commit with Unified Sync (1 RTT):** Client submits an operation with its `MutationId`, `CorrelationId`, and its current cursor `last_ack_seq`. The server validates the mutation against schemas and constraints. If valid, the server assigns a monotonic `SequenceNumber` and returns `CommitAck` containing the assigned `SequenceNumber` along with any remote catchup deltas (`catchup_ops: Vec<SequencedOperation>`) that occurred between `last_ack_seq` and the new sequence (and `has_more: bool` pagination indicator). This allows the client to register the write, sync pending state, and apply canonical data locally in a single network roundtrip (1 RTT) without risk of local state corruption.
    - **Ordering:** registration, then `last_ack_seq <= head_seq` (`InvalidSequence` otherwise), then a retried `MutationId` is acknowledged, with its original `SequenceNumber` and a catch-up starting at the client's `last_ack_seq`. Only then is the client checked against the retention boundary: if `last_ack_seq < tail_seq - 1` the commit is rejected with `BehindCompaction` before being sequenced, leaving no trace in the log, the head or the SSE stream. The client becomes `Bootstrapping`, and the room asks for a snapshot, unless its stored cursor is still inside the log (then the cursor in the commit was only stale). Schema validation comes next, then the operation size check (see *Size of a single mutation*; `BadRequest`). The lifecycle state is not a reason to reject: a `Bootstrapping` or `Dormant` client with a valid `last_ack_seq` commits and becomes `Connected`.
    - **Cursor advance:** an accepted commit (fresh or a deduplicated retry) advances the client's cursor to its `last_ack_seq` (never backwards), so clients that only write still move the retention floor, refreshes its lease and recomputes its state. Rejected commits never touch the cursor.
    - **Durable commits are always acknowledged:** once the mutation is written to `active.wal`, the reply is always a `CommitAck`. If the catch-up batch cannot be built, it is returned empty with `has_more: true`, directing the client to `/sync`, which reports the underlying error.
    - **Catch-up size:** the catch-up holds at most 100 operations and at most `MAX_RESPONSE_OPS_BYTES` of them; if operations are left out it is flagged `has_more: true`. It always holds at least one operation when any is pending, since every accepted operation fits alone.
  * **Synchronization (Standalone / Polling):** Client requests operations starting from its `last_ack_seq` specifying a maximum batch size (`ClientMessage::Sync`). The server streams ordered `SequencedOperation` batches with pagination flags (`has_more`). A batch holds at most `max_batch_size` operations (clamped to 1–1000) and at most `MAX_RESPONSE_OPS_BYTES` of them, but always at least one when any is available; a batch cut short is flagged `has_more: true`. `from_seq` above `head_seq` is `InvalidSequence`; below `tail_seq - 1` it is `BehindCompaction` (and, as for commits, the room asks for a snapshot if the client is left `Bootstrapping`). A served sync confirms everything up to `from_seq`: the client's cursor advances to it (never backwards) and the client becomes `Connected`, whatever its previous state.
  * **Acknowledgment:** `ClientMessage::Ack` advances the client's cursor (never backwards) and may trigger proactive pruning. `ack_seq` above `head_seq` is `InvalidSequence`. An ack below the stored cursor (stale or out of order) is a successful no-op. Retention is checked against the cursor the client ends up with: if it is behind the log the ack is rejected with `BehindCompaction`.
  * **Heartbeat:** `ClientMessage::Heartbeat` is lightweight liveness: it refreshes the lease and recomputes the client's state from its stored cursor, without moving the cursor. It never fails because the client fell behind the log (a client behind it becomes `Bootstrapping` and the room asks for a snapshot). `ServerMessage::HeartbeatAck { current_head_seq, snapshot_wanted, active_snapshot_seq }` tells the client whether it is the designated snapshot uploader and which snapshot it can bootstrap from (`active_snapshot_seq` is only reported if usable: $\text{tail\_seq} - 1 \le S \le \text{head\_seq}$).
  * **Orderly Deregistration (`DeregisterClient` -> `DeregisterAck`):** Client notifies orderly departure via `POST /rooms/{room_id}/deregister`, receiving `ServerMessage::DeregisterAck` over `application/octet-stream` with `StatusCode::OK` and removing the client from the room roster.
  * **Error Handling:** Every error carries an `ErrorCode`, and clients decide how to react from the code (Data Plane: in a binary `ServerMessage::Error` frame; Control Plane: in a JSON body `{ code, message }`). Codes and HTTP statuses:

    | `ErrorCode` | HTTP | Meaning and client reaction |
    |---|---|---|
    | `BadRequest` | 400 | Malformed request: an invalid identifier in the URL path, the binary payload or admin JSON, an undecodable body, a message of the wrong kind for the endpoint, a payload `room_id` that differs from the path, invalid relay parameters, a mutation too large to log or return (see *Size of a single mutation*), or a Data Plane path or method that does not exist (with HTTP 404/405). 413/415 keep their status (body too large, missing JSON content type). Not retried. |
    | `ProtocolVersionMismatch` | 400 | The request frame has another protocol version (see the version mismatch rule above). |
    | `SchemaViolation` | 400 | The operation does not match the room schema. |
    | `InvalidSequence` | 400 | A sequence above the room's head (`current_seq`, `last_ack_seq`, `from_seq`, `ack_seq`). |
    | `Unauthorized` | 401 | Token or admin secret missing, malformed, wrongly signed or expired: get a new token. |
    | `Forbidden` | 403 | Valid token that does not grant the request: issued for another room, or the message names another client. Permanent for that token. |
    | `RoomNotFound`, `SchemaNotFound` | 404 | The room or schema does not exist (also: no usable snapshot staged for the room). |
    | `RequestTimeout` | 408 | The request body did not arrive in time (see the body limits in [7.3](#73-http-edge-transport-and-limits)). Transient: retry with backoff (commits are deduplicated by `MutationId`). |
    | `ClientNotRegistered` | 409 | The client is not in the room's roster: register again. |
    | `RoomAlreadyExists`, `SchemaAlreadyExists`, `SnapshotSuperseded` | 409 | Conflicting state: the room or schema id is already taken (a schema is declared once and evolves only by adding columns), or see the snapshot relay for `SnapshotSuperseded`. |
    | `BehindCompaction` | 410 | The client's cursor is behind the retained log (`cursor < tail_seq - 1`): bootstrap from a snapshot. |
    | `RoomLocked` | 423 | The room's files are locked by another process. |
    | `RateLimited` | 429 | Too many concurrent single-request snapshot uploads for the room. |
    | `Internal` | 500 | Unexpected failure (I/O error, corrupted data, a bug, including a room actor that panicked while handling this request). Not retried automatically. |
    | `Unavailable` | 503 | The room cannot answer now: it is restarting after a failed commit write, or its actor stopped or dropped the request (also a request that was queued behind one that made the actor panic). The response carries `Retry-After: 1`; retrying is safe (commits are deduplicated by `MutationId`). |
    | `Timeout` | 504 | The room actor did not answer in time (5 s; every request to a room actor is bounded, including the relay's log range query and the admin room metrics). Retrying is safe. |
  * **Retention Contract (`tail_seq`):** `tail_seq` (in `Registered` and the admin room metrics) is the first sequence number the room log still retains; `head_seq` is the last committed one. A new room has `tail_seq = 1` and `head_seq = 0`; a log pruned completely has `tail_seq = head_seq + 1`, so `tail_seq` can exceed `head_seq` by one and clients must not assume `tail_seq <= head_seq`. A client at cursor `c` (everything up to `c` applied) can catch up from the log iff `c >= tail_seq - 1`; otherwise its operations get `BehindCompaction`. A snapshot at sequence $S$ is usable iff $\text{tail\_seq} - 1 \le S \le \text{head\_seq}$. The server evaluates both conditions with one shared implementation (`log::retention`).
* **Optional Foreground Streaming:** While a client application is actively in the foreground, it can establish an ephemeral push channel (SSE: `GET /rooms/{room_id}/events` authenticated via `EventStreamAuth`) to receive real-time notifications of new commits (`event: head_advanced`, data: the new head), DDL schema migrations (`event: schema_reloaded`, data: the schema id), a new snapshot uploader designation (`event: snapshot_wanted`, with an empty data line; whoever receives it sends a heartbeat to learn whether it is the designee) and a new usable snapshot (`event: snapshot_available`, data: its sequence). These events only speed clients up: SSE is optional and a slow subscriber can miss events (`event: lagged`), so the replies to heartbeats, syncs and commits remain the source of truth.
* **Graceful Shutdown (`serve_until_shutdown`):** On SIGINT or SIGTERM (on Windows: Ctrl+C, console close or system shutdown) the server stops accepting connections and fires a shared `ShutdownSignal` that ends every open SSE stream, closes at once every connection without a request in progress (including one still sending its headers), waits for in-flight requests and the writing of their responses (a connection is closed once it has been idle for 1 s, without waiting for the client to confirm the end of an HTTP/2 connection), then shuts down all room actors, each of which persists its client roster. If this takes longer than 10 s the process exits anyway; acknowledged commits are already durable.

### 7.3. HTTP Edge: Transport and Limits
* **Transport:** The server listens on plain TCP and speaks HTTP/1.1 and HTTP/2 without TLS (h2c with prior knowledge), told apart by the first bytes of each connection. It does not terminate TLS: it is deployed behind a reverse proxy that terminates TLS and talks HTTP/2 (or HTTP/1.1) to the clients. Without such a proxy, client tokens and the admin secret travel in clear text.
* **Limits (`serve_until_shutdown`):** Every connection, over either HTTP version, is subject to:

  | Setting (TOML) | Environment variable | Default | Accepted | Behavior |
  |---|---|---|---|---|
  | `header_read_timeout_secs` | `ZEMDB_HEADER_READ_TIMEOUT_SECS` | 10 | 1 – 300 s | A connection must deliver the headers of each request within this time, counted from its opening or from the end of its previous response. A client that does not (slow headers, a connection that sends nothing, an idle keep-alive or HTTP/2 connection) is disconnected. |
  | `body_read_timeout_secs` | `ZEMDB_BODY_READ_TIMEOUT_SECS` | 60 | 1 – 3,600 s | Base time for a request body to arrive in full, counted from the end of its headers and extended as data arrives (next row). A body still incomplete at its deadline fails with `ErrorCode::RequestTimeout`, HTTP 408 (a binary frame in the Data Plane, JSON in the Control Plane). |
  | `body_min_rate_bytes_per_sec` | `ZEMDB_BODY_MIN_RATE_BYTES_PER_SEC` | 32,768 (32 KiB/s) | 1 KiB/s – 1 GiB/s | Each time this many bytes of the body arrive, its deadline moves one second later (as Apache's `mod_reqtimeout`). A body that arrives at least this fast is never cut, however large: with the defaults, a 16 MiB body may take up to 60 s + 512 s. One that trickles in slower gains next to nothing and is cut close to the base time. |
  | `max_connections` | `ZEMDB_MAX_CONNECTIONS` | 10,000 | 1 – 1,000,000 | Connections served at once. At the limit the server stops accepting until an open connection closes (new ones wait in the listen backlog); open connections are not affected. |

  An HTTP/2 connection carries at most 100 requests at once (`MAX_CONCURRENT_STREAMS`), so `max_connections` also bounds the requests in flight.

  Request bodies are limited to `MAX_FRAME_SIZE` (16 MiB + 4 bytes), except `POST /rooms/{room_id}/register`, limited to `MAX_REGISTER_BODY_SIZE` (64 KiB): a `RegisterClient` frame takes a few hundred bytes and the endpoint reads its body before any authentication, so a large body sent quickly and then held back short of its end cannot keep its buffer for as long as the minimum body rate allows. A larger body is a binary `BadRequest` frame with HTTP 413, as for the general limit.

  A request in progress, including the writing of its whole response at the client's pace, is never cut by these limits: the header timeout of HTTP/1.1 starts once the previous response is fully written, and over HTTP/2 a response stays in progress until the client has accepted all of it but its last frame (64 KiB), and the connection then counts as active while its writes keep making progress. The two protocols differ for a client that stops reading a response: over HTTP/1.1 it keeps the connection, because hyper has no write timeout; over HTTP/2 it is disconnected once the header timeout passes without its writes making progress. An SSE stream (`/events`) has no body to read and stays open as long as the client and the room keep it. Each connection takes a file descriptor, so the process limit of open files (`ulimit -n`, often 1,024 by default on Linux) must be above `max_connections` plus the files the rooms keep open. Values are parsed and range-checked like the other settings ([5.3](#53-configurable-lifecycle-policy-roomlifecyclepolicy)): an invalid value makes the server refuse to start, naming the variable.

## 8. Storage Engine (`zemdb-storage`)

Persisting data locally on clients and managing snapshots is decoupled into a dedicated storage crate implementing a common `StorageEngine` abstraction:
* **The `StorageEngine` Contract:**
  * Clean, network-agnostic async persistence contract: `open_room`, `close_room`, `apply_batch`, `get`, `get_by_id`, `scan`, `scan_by_id`, `get_head_seq`, `create_snapshot`, `apply_snapshot`.
  * **Direct ID Queries (`get_by_id` & `scan_by_id`):** Trait methods accept direct numerical table identifiers (`table_id: u16`), eliminating secondary string lookup overhead in the inner query pipeline. Queries by name (`get`, `scan`) resolve the name and read the rows under a single acquisition of the room's read lock, so the name is translated against the schema those rows belong to.
  * **Active Storage Schema Validation:** `StorageEngine::apply_batch` validates every sequenced operation directly against `schema.validate_operation(&op.op)?` across both `MemoryStorageEngine` and `DiskStorageEngine`, preventing corrupt or mismatched rows from being committed to WAL or memory state.
  * **Universal Canonical Snapshot Envelope (`ZMSN`):** Snapshots across all storage engines share a standardized envelope with 4-byte magic `"ZMSN"`, version `1`, compression algorithm flag (0 = Raw/Memory, 1 = Zstd/Disk), original uncompressed length, and CRC32 checksum. This guarantees 100% cross-engine snapshot portability: snapshots created by `MemoryStorageEngine` can be applied directly by `DiskStorageEngine` and vice versa with automatic Zstd decompression. The header definition and its validation (`SnapshotEnvelopeHeader`, `validate_snapshot_envelope`, the incremental `SnapshotEnvelopeValidator`) live in `zemdb-core` (`protocol::snapshot_envelope`), shared by `zemdb-storage` and the server's snapshot relay; storage adds compression and decompression.
  * **Bounded Snapshot Decompression:** The declared uncompressed length is never trusted. `decode_snapshot_envelope` rejects an envelope declaring more than 2 GiB (`DEFAULT_MAX_SNAPSHOT_UNCOMPRESSED_BYTES`; `decode_snapshot_envelope_with_limit` and `DiskStorageOptions::max_snapshot_uncompressed_bytes` set another limit) before decompressing, decompresses with a streaming decoder that stops one byte past the declared length, and fails unless the output has exactly the declared length. The up-front buffer reservation is capped at 64 MiB.
  * **Zero-Copy Move Semantics:** `apply_batch` takes `Vec<SequencedOperation>` by ownership value, eliminating redundant cloning between client network pipelines and local storage.
  * **`apply_snapshot` Rules (both engines):** The room must be open (`StorageError::RoomNotFound` otherwise, checked before the snapshot is decoded). A snapshot whose `head_seq` is behind the room's is rejected with `StorageError::SnapshotBehind { current, snapshot }`: a room never moves back. A snapshot at the room's `head_seq` changes nothing and succeeds, so a retried apply is idempotent (without offline writes, the room at a sequence number already equals any snapshot taken at it); the schema passed with it is ignored too. A snapshot ahead replaces the schema, `head_seq` and every table in place, under the room's lock: the room's handle is never swapped, so a writer that already holds it writes into the new state, not into a detached copy.
  * **WebAssembly (WASM) Ready:** Defined with conditional concurrency bounds `#[cfg_attr(target_arch = "wasm32", async_trait(?Send))]` and platform-specific `RowStream<'a>` definitions, allowing native execution in single-threaded browser environments (e.g. IndexedDB).
* **Pushdown Query Capabilities (`ScanOptions`):**
  * Modern storage abstraction supporting query execution without bloating the storage engine with SQL parsers:
    * `KeyRange`: Flexible range bounds conforming to Rust standard range syntax (`..`, `a..b`, `a..=b`, `a..`).
    * `ScanDirection`: Forward (`ASC`) and Backward (`DESC`) for $O(1)$ memory `ORDER BY pk DESC` traversal.
    * `limit: Option<usize>`: Early I/O termination pushdown avoiding scanning unwanted records.
    * `projection: Option<Vec<u16>>`: Projection pushdown returning compact rows with only requested column indices, preventing unnecessary deserialization.
* **In-Memory Reference Engine (`MemoryStorageEngine`):**
  * Thread-safe memory backend with **per-room lock isolation** (`Arc<RwLock<HashMap<RoomId, Arc<RwLock<RoomState>>>>>`). The room state and its handle are internal to the crate: users read and change rooms only through the `StorageEngine` methods, which validate every change.
  * Operations across different rooms run 100% concurrently without lock contention. Within each room, multiple concurrent readers execute in shared mode (`read()`) while mutation batches take an exclusive lock (`write()`) on that specific room only.
  * Tabular data stored in persistent ordered maps (`imbl::OrdMap<PrimaryKey, CompactRow>`, the storage `Table` type) with binary snapshot serialization. Cloning a table is O(1) and shares its nodes; a write to either copy duplicates only the O(log n) nodes on the path to the written key. A scan keeps such a clone, so a write during a scan (or during a compaction, in the disk engine) never copies the whole table. The maps serialize as maps in key order, exactly like `BTreeMap`, so the snapshot format is unchanged. Pure Rust, with serde, and builds for `wasm32-unknown-unknown`.
* **On-Disk Engine (`DiskStorageEngine`) [IMPLEMENTED - Phase 2B & 2.8]:**
  * **Dual-File Architecture:** Separate physical files per room:
    * `room_{id}.snap`: Immutable base snapshot with 64-byte `ZEM1` header, schema fingerprint, and Zstandard block compression.
    * `room_{id}.wal`: Append-only Write-Ahead Log (WAL) containing batched mutational deltas framed with `0xBA7C` magic, payload length, unified CRC32, and operation count.
  * **Physical WAL Framing in Core, One Decoder for Torn Writes:** Framing definitions and batch codecs are centralized in `zemdb-core` (`protocol::wal_frame`) and shared directly by `zemdb-storage` and `zemdb-server` (Tier 2 Warm Disk Log). The decoder is split into sans-I/O primitives (`parse_batch_header`, `decode_batch_payload`, `classify_checksum_mismatch`, `classify_zeroed_header`): `decode_wal_batch_from_slice` is built on them, and `recover_room`, which streams the WAL from disk instead of loading it, uses the same ones, so both tell a torn write from corruption identically. The end of the valid log is a torn write, truncated in place to `valid_wal_bytes`, when it is an incomplete header or payload, a zero-filled tail (a zeroed header followed only by zeros, as left by thin-provisioned or pre-allocated file systems), or a frame whose CRC32 does not match and is not followed by a complete frame header. A CRC32 mismatch followed by a complete frame header means a durable frame comes after the damaged one, and is reported as `WalCorruption` instead of silently dropping the tail; any other invalid magic is corruption too. Streaming reads fill each buffer completely before deciding, so the decision never depends on where a read buffer happens to end. `WalReader` (slice reader, used by tools and tests) returns whole batches and skips frames without operations. During recovery, operations at or below the current `head_seq` are skipped, so records already in the snapshot, or duplicated across files by a crash during compaction, are never applied twice. A record that does not continue the sequence exactly (`head_seq + 1`) is a gap and fails recovery with `WalCorruption`.
  * **Zero-Copy Snapshot Streaming (Anti-4x RAM Spike):** Both in-memory and on-disk snapshot generators serialize tables directly by reference (`RoomSnapshotRef<'a>`) into the Zstandard compressor, eliminating full database allocations and row cloning. The disk engine takes O(1) clones of the tables under a brief shared lock and serializes and compresses them on the blocking pool, without holding the room's lock. Snapshot hydration assigns deserialized table trees (`RoomSnapshotPayload`) directly into memory state without intermediate vector-to-map transformations.
  * **WAL Mutex Separate from the Readers' Lock:** Each open room has three locks, always taken in this order: a compaction lock, a WAL mutex and a read-write lock over the in-memory state. The compaction lock excludes compactions, `apply_snapshot` and `close_room` from each other; it belongs to the open room instance, so an operation that waited for it across a close (and a reopen) gives up with `RoomNotFound` instead of working on the reopened room. A batch holds the WAL mutex while it is validated (against the head of the last batch in the WAL), appended, `fsync`ed and applied in memory. It applies its operations to O(1) clones of the tables and takes the state lock exclusively only to publish them, so readers see all of a batch or none of it, even if applying it panics. Readers take the state lock shared and never wait for an `fsync`. Because each batch is applied before the WAL mutex is released, memory follows WAL order, and since only durable batches are applied, readers always observe a prefix of the WAL. Compaction's WAL rotation (phase 1) and `apply_snapshot` also hold the WAL mutex, so no batch is ever between its WAL write and its memory application while the WAL moves or is replaced. A batch abandoned in that window (an I/O error, a panic, or its future being dropped) leaves memory behind the WAL, so a guard marks the room as failed when it drops before the batch is applied. The same guard covers every other multi-step change of the files under the WAL mutex (a WAL rotation or absorption, emptying the WAL, installing a snapshot): `tokio::fs` operations complete on the blocking pool even when the future awaiting them is dropped, so a change abandoned halfway could leave the WAL handle pointing at a renamed file, or past the end of an emptied one. `DiskStorageEngine::compact_room` runs the compaction in its own task, so a caller that stops waiting never abandons it.
  * **Non-Blocking Background Copy-on-Write (CoW) Compaction:**
    * Phase 1 (WAL mutex; readers are not blocked): the active `room_{id}.wal` is renamed to `room_{id}.wal.compacting` and a fresh, locked `room_{id}.wal` takes incoming writes; the directory is synced. If the fresh WAL cannot be opened, the rename is rolled back so writes keep landing in the active WAL. If a previous compaction failed and left `.wal.compacting` behind, the active WAL is appended to it (and synced) before being truncated, so the orphan is never overwritten.
    * Phase 2 (background): the captured tables are compressed into a synced `room_{id}.snap.tmp.{uuid}`. In-flight writes to `room_{id}.wal` are never blocked.
    * Phase 3 (no room lock during the I/O): the temporary file is atomically renamed over `room_{id}.snap`, then `.wal.compacting` is removed, syncing the directory after each step. Writers only touch the active WAL, and the compaction lock keeps out other compactions and `apply_snapshot`; the state lock is taken briefly to record the new snapshot's sequence and size.
    * The compaction flag is an atomic released by a guard on drop, so a failure at any step never leaves compaction permanently disabled.
  * **Crash-Safe `apply_snapshot`:** The snapshot is staged into a synced temporary file under the compaction lock only, so writers keep going meanwhile. Then, under the WAL mutex, the head is checked again (a snapshot that writers have reached is discarded as a no-op, one they have passed is rejected, and in both cases the temporary file is removed), the file is renamed over `room_{id}.snap` (directory synced), and only then are the active WAL emptied and any `.wal.compacting` removed; memory is replaced last, so readers see the previous state until the new one is durable. A failed staging or rename changes nothing on disk: the temporary file is removed and the room stays usable (a temporary file left by a cancelled call is removed when the room is next opened). A crash before the rename leaves the previous files intact (recovery removes the temporary file). A crash after it leaves records in the WAL files that are all at or below the new snapshot's sequence, which recovery skips. This only holds because a snapshot behind the room is rejected: its records between the two sequence numbers would otherwise be replayed on top of it. A failure after the rename, or a call abandoned from the rename on, marks the room as failed.
  * **Crash-Safe Recovery of an Interrupted Compaction:** On open, a leftover `.wal.compacting` is replayed before the active WAL. If it held live records, a fresh snapshot of the recovered state is written through the atomic path, the active WAL is emptied, and only then is `.wal.compacting` removed. Files are never rewritten in place and the locked WAL handle is never swapped, so a crash at any step leaves files that a later recovery replays to the same state.
  * **Failed Room State on Uncertain I/O:** If a WAL write or `fsync` fails (including the WAL sync before a compaction and the directory sync after a rotation), if a change of the files under the WAL mutex is abandoned halfway, if a rotated WAL cannot be restored after a failed rotation, or if an applied snapshot cannot be installed after its rename, the on-disk state is no longer known from inside the process (a failed `fsync` cannot be safely retried). The room is marked as failed: writes and compactions return `StorageError::RoomFailed` until it is closed and reopened, so that recovery rebuilds it from what is actually on disk. During compaction the active WAL is read through its own locked handle (a second handle cannot read a locked file on Windows), and a partially failed append to `.wal.compacting` is truncated back to its previous length (the file is opened for writing and positioned at its end, not in append mode: on Windows an append-only handle cannot be truncated). Directory syncs during compaction and recovery run on Tokio's blocking pool, like the `tokio::fs` calls around them.
  * **Non-Blocking Chunked Scan Streams:** Scans stream items in chunks (64 tuples), releasing read locks between chunks to eliminate writer starvation.
  * **Multi-process exclusive file locking (`flock`):** Active process holds exclusive lock on the `.wal` file, preventing simultaneous mutations from concurrent processes.
  * **RAM-Resident Primary Index:** Tabular memory state in `imbl::OrdMap<PrimaryKey, CompactRow>` (see the in-memory engine) enables $O(\log n)$ point lookups without disk reads.
  * **Zero Global Lock Contention on File Sync (`close_room`):** In `DiskStorageEngine::close_room`, the room is extracted and the engine-level write lock is dropped *before* executing asynchronous disk sync (`wal_file.sync_all().await`), preventing file I/O operations from blocking access to other rooms across the engine. The sync takes the room's WAL mutex, so it waits for a batch in progress to finish.

## 10. Architectural Decisions: Time, Ordering & Authority

### 10.1. Central Server Sequencer as the Sole Authority of Total Order
A foundational architectural decision of ZemDB is that **the coordination server is the single source of truth for global ordering**:
* **Sequence-Based Total Order:** When an operation is accepted by the Room actor on the server, it is assigned an atomically increasing `SequenceNumber`. The global order of events in the Room is defined 100% by this monotonic sequence number.
* **No Trust in Client Wall Clocks:** Client devices frequently suffer from clock skew (misconfigured system times, zone errors, drift). To eliminate the risk of a misconfigured device clock dominating or corrupting the room's history, **client timestamps are never used to determine global causal precedence**.
* **Deterministic Last-Write-Wins (LWW):** In the event of concurrent modifications to the exact same field, the operation with the higher `SequenceNumber` (the one processed later by the server sequencer) takes precedence. This eliminates the necessity of complex Hybrid Logical Clocks (HLC) while guaranteeing absolute convergence across all nodes.

### 10.2. The Three Concepts of Time in ZemDB
To prevent conceptual ambiguity, the architecture distinguishes three independent notions of time:
1. **`SequenceNumber` (Total Order Authority):** Monotonic integer issued exclusively by the server. Defines causal precedence, commit ordering, and conflict resolution across all clients.
2. **Mutation `timestamp: u64` (Client Metadata):** Client-generated timestamp attached to mutations for audit/tracing purposes. Not used for causal precedence or local optimistic rebase.
3. **Domain `Value::Timestamp(i64)` (Application Data):** Structured column data type used by end-user schemas to store business dates and timestamps (e.g., `created_at`, `due_date`).
